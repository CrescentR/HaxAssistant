# HaxAssistant 数据维护策划案

HaxAssistant 的个人自用版从 AramHex 导入国服海克斯大乱斗统计。每次导入成功都保存一份独立快照，当前版本由一个小文件指向。新数据上线只切换这个指针，已有快照在保留期内仍可查看和恢复。第一版用本地文件和定时检查即可。

## 数据来源与导入范围

数据源定为 `czgreat/aramhex-data`，使用其 CC BY-NC 4.0 发布的统计，在应用的数据来源区域保留署名和链接。[AramHex 数据仓库](https://github.com/czgreat/aramhex-data) · [字段与采集说明](https://github.com/czgreat/aramhex-data/blob/main/AGENTS.md)

| 用途 | 上游文件 | 第一版行为 |
| --- | --- | --- |
| 发现更新 | `latest.json` | 读取版本、规则、序号 `seq`、数据截止时间、目录和文件哈希 |
| 回查历史 | `index.json`、`data-v<seq>` 标签 | 用索引查版本和规则，用标签或对应提交取固定快照 |
| 英雄与海克斯推荐 | `heroes.json`、`hero_augments.json`、`augments.json` | 按 ID 关联，保留胜场、样本和低样本标记 |
| 统计口径 | `meta.json` | 保留样本时间窗、有效对局数和筛选规则 |
| 装备统计 | `hero_item_holdings.json`、`equipment_heroes.json` | 可后续接入，使用装备统计自己的分母和版本 |

首版自动启用常规规则 `normal`。同一 Patch 可以有多个序号，活动规则将来接入时按规则区分。三海克斯组合和阶段收益等字段缺少观测数据时，界面显示暂无数据。多份快照的时间窗可能重叠，直接相加会重复计数，所以历史页按每份快照原有口径展示。[版本清单](https://raw.githubusercontent.com/czgreat/aramhex-data/main/latest.json) · [数据说明](https://github.com/czgreat/aramhex-data/blob/main/AGENTS.md)

## 快照目录与保留期限

文件放在应用的本地数据目录中。正常更新时，已验收的快照按只读文件处理。下图里的路径和快照编号用于说明文件布局。

```text
data-cache/
  latest.json                 最近一份通过校验的可用快照
  active.json                 当前推荐使用的快照
  snapshots/
    aramhex/16.23/normal/
      seq-20/
        manifest.json
        source.tar.gz         本次实际用到的上游 JSON
        runtime/              供 HaxAssistant 读取的 JSON
      seq-22/
        manifest.json
        source.tar.gz
        runtime/
```

快照清单记录来源、Patch、规则、上游序号、固定引用、统计时间窗、有效对局数、导入时间、转换器版本和文件 SHA-256。历史列表按上游数据截止时间排序。以 `来源 + Patch + 规则 + seq` 判断是否已导入。遇到相同序号而上游内容哈希变了，保留已验证快照并记录异常，等待可验证的新输入。

| 保存位置 | 建议保留策略 |
| --- | --- |
| 最近历史 | 最近 90 天内，每份成功导入的快照都保留 |
| 较早历史 | 每个游戏 Patch 保留一份采集到的最后快照，留作历史比较 |
| 恢复用 | 始终保留当前使用的快照和最近一份已知可用的回退快照 |
| 占用估算 | 当前清单中四份核心原始 JSON 合计约 2.46 MB 未压缩。按每天一份估算，90 天约 222 MB，仅计原始输入。实际体积取决于上游发布频率、压缩率和转换后文件大小 |

90 天是个人版的建议默认值。仅在新快照完成写入和验证后执行清理，待回退或手动固定的快照始终保留。刚接入时可以用上游保留的版本标签补回可取得的历史快照，再按同一规则整理。[上游清单与文件大小](https://raw.githubusercontent.com/czgreat/aramhex-data/main/latest.json)

## 自动更新与失败恢复

1. 桌面端启动先加载当前快照，后台检查新版本。运行期间每六小时最多检查一次，同一时间只运行一个导入任务。重新启动发现中间跳过了序号时，可从仍可访问的上游标签补齐保留期内的历史。应用关闭期间由下次启动补查。
2. 发现新序号后，从固定标签或提交下载到临时目录，校验文件哈希、版本、必需字段与 ID 关联。保留这次实际使用的原始文件，生成桌面端所需的 JSON。用真实数据加载器试读通过后，再将临时目录移到最终位置。
3. 原子写入 `latest.json`。客户端处于跟随最新模式时，在合适的对局间隙同步切换 `active.json`，并让主窗口和悬浮窗一起重读。手动回退时固定 `active.json`，之后仍可继续接收新的历史快照，恢复跟随后再启用最新数据。
4. 网络、解析、哈希或加载失败时，继续用现有的 `active.json`，记录失败原因并在下次检查时重试。首次启动或本地缓存损坏时，按「当前有效快照 → 最近可用快照 → 安装包自带数据」恢复。若要在电脑关闭期间持续归档，可把同一导入任务放进 GitHub Actions，由桌面端择机下载。

设置、玩家标记等用户数据放在固定目录。历史浏览按指定快照读取，当前对局推荐由 `active.json` 决定。现有更新器逐个写入数据文件，因此启用自动更新前，先把写入和切换改成整包操作。[现有更新器](../crates/data-updater/src/lib.rs#L274) · [数据加载和用户状态](../crates/app-core/src/lib.rs#L85)

## 实施顺序与验收

1. **先跑通本地归档。** 用同一 Patch 的两份固定上游快照验证转换，检查第二份导入后第一份的文件哈希和目录仍一致。重复运行同一序号时应复用已有快照。
2. **接入桌面端自动更新和恢复。** 验证断网、校验失败、中断重启都能继续使用上一份数据。新数据切换后，主窗口和悬浮窗应显示同一快照。
3. **补齐历史查看和保留策略。** 在设置里显示版本、规则、更新截止日期、样本量和来源。能查看历史快照、手动回退和恢复跟随最新，并验证清理时保留当前及回退快照。

保存多份 JSON 的实现量较小。主要工作是让下载失败时旧数据照常可用，并让主窗口和悬浮窗始终读到同一份快照。若以后需要跨大量版本筛选和画趋势图，可以在已有快照上建立本地 SQLite 索引。
